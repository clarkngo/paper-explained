Allowing Generative AI in CS1 with Code Review Interviews and a Flipped Classroom

Core Problem and Proposed Solution

Students in introductory programming (CS1) courses increasingly use LLMs to generate code, which risks letting them submit working assignments without building the debugging and reasoning skills CS1 is meant to teach. Rather than trying to detect or ban AI use, which is unreliable and easy to route around, the authors propose verifying understanding directly:

  • Weekly oral code review interviews: Students must explain their own submitted code, regardless of whether an LLM helped write it.
  • Flipped classroom: Concepts are learned outside class, freeing in-class time to run the interviews.

Methodology

  • Data: Three semesters of a CS1 course, including exam scores, keystroke logs, and end-of-term student surveys.
  • Intervention semester: Fall 2025, when the code review and flipped-classroom policies were introduced.
  • AI-use proxy: Ratio of pasted characters to total characters typed on coding assignments, measured from keystroke logs.
  • Comparison: Pairwise comparison of exam scores against prior semesters.

Learning Framework Breakdown

To help master the core ideas, this section explains the paper using multiple learning frameworks, moving from definitions to intuition, root-cause reasoning, and practical examples.

1) Glossary of Key Terms

  • CS1: The first programming course in a computer science curriculum, typically focused on fundamentals like variables, control flow, and basic data structures.
  • Oral code review interview: A short, spoken assessment where a student explains their own code to an instructor or TA, used here as a weekly formative check.
  • Flipped classroom: A course structure where students learn new material outside of class (readings, videos) and use class time for applied work and assessment instead of lecture.
  • Keystroke logging: Recording how a student typed their submission (including pasted text) to estimate how much of the code came from an external source like an LLM.
  • Verification-based assessment: Checking that a student understands a result, rather than trying to confirm how the result was produced.

2) ELI5 (Explain Like I am Five)

Imagine a cooking class that lets you use a recipe app. But every week, the chef stops by your station and asks you to explain, out loud, why you're adding salt now instead of later. You can use the app — but you still have to understand the dish you're making. If you can't explain it, the chef knows, no matter how good the plate looks.

3) The 5 Whys (Root Cause Analysis)

Goal: Understand why verifying understanding, rather than restricting tools, is the proposed fix.

  1. Why allow generative AI in a CS1 course at all? Because students already use it, and banning it is largely unenforceable.
  2. Why is that risky for a first programming course? Because CS1 is where students are meant to build foundational debugging and reasoning skills, which pasted code can bypass entirely.
  3. Why use oral code review instead of tighter AI bans or detectors? Because it verifies whether the student understands the code directly, rather than trying to detect AI authorship, which is unreliable.
  4. Why pair it with a flipped classroom? Because running weekly one-on-one interviews for an entire class needs in-class time that a traditional lecture format doesn't have.
  5. Why does unchanged exam performance matter here? Because it suggests verification-based assessment can neutralize the downside of heavier AI use, instead of needing to eliminate AI use itself.

4) Example Scenario

A student pastes a ready-made sorting function from an LLM into their assignment. At the weekly code review, a TA asks: "Why did you choose this sort for this input, and what happens if the list has duplicates?" The student has to answer live. If they can't, it surfaces a gap in understanding immediately — before it compounds into later, harder courses that assume CS1 fundamentals are solid.

Key Findings and Insights

  • No drop in exam scores: A pairwise comparison found no statistically significant change in average exam scores for Fall 2025 versus previous semesters, despite allowing AI use.
  • AI use clearly increased: Keystroke logs showed a significant rise in the ratio of pasted-to-typed characters on coding assignments in Fall 2025.
  • Positive student reception: End-of-semester surveys showed positive sentiment toward the code review interviews.
  • Friction was logistical, not conceptual: Nearly all negative feedback related to scheduling and TA consistency, which the authors say is addressable through better scheduling tools and more rigorous TA training.

Practical Applications

  • Shift the strategy: Move from an AI-detection arms race toward oral or other verification-based checks of understanding.
  • Restructure the course, not just the policy: A flipped classroom is likely necessary to create the in-class time these interviews require.
  • Invest in the rollout: TA training and scheduling infrastructure were the main sources of friction, not the core idea.

Caveats

As an arXiv preprint, the paper reports qualitative and directional results (no significant change, a significant increase in pasted characters, positive survey sentiment) without published sample sizes, effect sizes, or p-values, so the numerical detail is limited to what the authors stated.
